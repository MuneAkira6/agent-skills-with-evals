# agent-skills-with-evals

Three [Claude Code](https://claude.com/claude-code) skills, each with an eval suite that is honest
about what it measured. A trigger-rate probe that tells a broken run from a negative one, a Redmine
fetcher where an attachment counts as fetched only when its bytes match the metadata, and a stand-up
digest where rules decide and a language model writes only short sentences behind a guard.

Every number in 「結果」 comes from a real run of the CLI on 2026-10-05 and is committed under
`evals/*/results/`. The headline is not a score: measured again at six runs instead of three, five of
the seven re-measured queries moved and two verdicts flipped.

---

## 何を示すか

このリポジトリが示すのは、**スキルを作る技術そのものより、スキルを測った結果を正直に読む方法**です。

- スキルが起動しなかったのか、測定器が壊れていたのかを**区別する**プローブ。
- 取得が成功したと言える条件を、「エラーが出なかったこと」ではなく**バイト数と内容**で定義した取得器。
- 規則で決められることは規則が決め、LLM には短い文しか書かせず、その文をガードに通すダイジェスト。
- そして、それぞれの**評価スイート**と、実際に `claude` を呼んで取った測定結果。

スキル 3 本はいずれも実務で使っていたものが元です。このリポジトリは、その作り方を公開できる形に
書き直し、**評価を足して、測って、測った数字をそのまま載せたもの**です。都合の悪い数字も含めて
載せているので、いちばん読んでほしいのは 「結果」 と 「制約・既知の限界」 です。

評価の読み方として残した教訓は [docs/reading-evals.md](docs/reading-evals.md) に分けて書いてあります。

## 背景

元になった実務の話は、別のリポジトリの事例としてまとめてあります。

> [06-ai-in-daily-engineering.md — engineering-case-studies](https://github.com/MuneAkira6/engineering-case-studies/blob/main/06-ai-in-daily-engineering.md)

実務で起きていたことを短く書くと、次の 3 つです。

1. **公式の評価ツールの起動判定が、Windows では毎回「起動しなかった」と報告していました。**
   しかもそれが失敗に見えませんでした。測定器が黙って壊れていると、「スキルが起動しない」という
   結果として読めてしまいます。そこで CLI を実際に起動して数える自前のプローブに置き換えました。
2. **添付ファイルの取得が、成功したように見えて失敗していました。** 中継装置が返す 403 の
   エラーページも、それらしい名前のファイルとして保存されてしまいます。保存したバイト数が
   メタデータのサイズと一致したかだけを、成功の条件にしました。
3. **朝会のページを毎日自動で作っていました。** 毎回違う一覧を出す既存の AI 機能は使いませんでした。
   同じデータからは同じ一覧が出ることに価値があるからです。

実務の件数・割合・費用・日付といった数字はこのリポジトリには書きません。上の事例を参照してください。
**このリポジトリに出てくる数字は、すべてこのリポジトリ自身の実行から取ったものです。**

## 設計

スキルディレクトリは**単独で成り立ちます**。`skills/<name>/` は Node の標準モジュールだけを使い、
npm の依存を持たず、ほかのスキルからも import しません。別のリポジトリにディレクトリを 1 つ
コピーすれば動くことが条件だからです（そのために、伏せ字の処理と CLI の起動は 2 か所に意図して
重複させています。理由は [goal-pack/SCOPE.md](goal-pack/SCOPE.md) の AS-BUILT に書きました）。
評価用の `harness/` と `test/` はスキルを import しますが、**逆向きは禁止**です。

### `skills/skill-trigger-probe` — 起動するかを測る

フロントマターを公開仕様に照らして検証し、同じ問いを複数回投げて起動率を測ります。

**実務で実施した点**

- 出力が空だった実行を「起動しなかった」ではなく**「測れなかった」として別に数える**こと。
  測定器が壊れていても「スキルが起動しない」という結果に見えてしまうからです。
- 説明文が公開仕様の上限を超えていて、末尾の除外条項がモデルに届かない状態になっていたのを
  検証ツールで見つけたこと。だから説明文の**文字数**を数えます。
- 説明文に「何をするか」「いつ使うか」だけでなく**「何には使わないか」**を書くこと。
  「しないこと」がないと、似たスキルの間で取り合いが起きます。

**デモで追加した点**

- 公開仕様と**出典**を付けたフロントマターの検証（`references/frontmatter-spec.md`）。
- 測れなかった実行を**理由ごとに**分ける判定。`spawn-error`、`timeout`、`no-init`、`no-result`、
  `auth`、`not-loaded` の 6 つを**この順で**先に見て、どれでもなければ起動の有無を見ます。
  順番が重要です。終了コードだけでは決められません（`error_max_turns` は終了コード 1 で正常、
  資格情報がないときは `subtype: "success"` で返ります）。
- **どのスキルが起動したか**の記録（`siblingsFired`）。率が 0 のとき、「何も起動しなかった」と
  「別のスキルが勝った」では直し方が正反対です。
- **閾値付近の警告**（`nearThreshold`）。信じてはいけない率に印を付けます。
- 設定を分離した測定（`isolatedConfig`）。測定が手元の設定に汚されないようにします。

### `skills/verifiable-fetch` — 取得できたと言える条件を決める

Redmine のチケットを Markdown と添付ファイルとして保存します。

**実務で実施した点**

- 添付の成功判定を**保存したバイト数とメタデータのサイズの一致**だけにしたこと。
- ログに出す URL で**署名部分を伏せる**こと。
- 保存先のパスを**短く保つ**こと。Windows ではパスが長すぎると、ディレクトリをたどる道具が
  エラーを出さずに空の結果を返すことがありました。
- 画像にはリンクを置くだけでなく、**何が写っているかを文章で**書き残すこと。後で検索する人の
  役に立つのはそちらです。

**デモで追加した点**

- Redmine の形をしたモックサーバ（`harness/mocks/tracker.ts`）と、別ホストのメディア配信。
- **検査の順番を固定**したこと。ステータス → Content-Type → サイズ の順です
  （`references/verification-rules.md`）。403 のエラーページは HTML なので、サイズを見る前に
  型で落ちます。
- 失敗を**失敗として報告する**こと。1 つでも検証に落ちた添付があれば、ページにその理由が載り、
  終了コードが変わります。「2 ok, 0 failed」という行が最後に出るのは、読み手が成功数を
  数えなくて済むようにするためです。

### `skills/standup-digest` — 規則が決め、LLM は書くだけ

GitHub リポジトリの現在のマイルストーンから、朝会用のページを 1 枚作ります。

**実務で実施した点**

- 泳道・今日決めること・並び順は**規則で決め**、LLM は規則が選んだ項目について短い文だけを書く。
  ガードを通らなければ、機械の文だけでページを出します。**表こそが本体**だからです。
- 「今日決めること」の件数を**固定しない**こと。規則に当たった項目がすべて載り、ない日は
  「ない」と書きます。
- 「動き」として数えるのは**状態の遷移、コメント、PR の更新、本文の編集だけ**。
  スプリント計画で一斉に行う移動や担当替えは数えません。それらは更新日時をまとめて新しくして、
  長く誰も触っていない項目を隠してしまいます。
- 朝会に出ない人が担当の項目は、決めごとに載せない。その場に決める人がいないからです。
- 進捗のない項目は「発言不要」として名前を出し、**黙ることに正当性を与える**こと。
- ページのコメント欄が翌日の指示の窓口で、**変えられるのは書き方だけ、事実は変えられない**こと。
- 安く済む作り。CLAUDE.md のないディレクトリで CLI を動かし、システムプロンプトを差し替え、
  ツールと MCP を外し、入力を絞り、思考は**その 1 回の呼び出しのプロセスにだけ**環境変数で
  止めます（設定ファイルには書かないので、ほかのセッションに影響しません）。入力が前回と同じなら、
  ガードを通った前回の文を使って**呼び出しません**。
- 評価で見つけた自分自身の欠陥：並び順の点数が、同じ停滞を**二重に数えていた**こと。足し算を
  やめて大きいほうだけを取り、何度も機会があった慢性の項目は割り引くようにしました。

**デモで追加した点**

- GitHub REST の形をしたモック（`harness/mocks/github.ts`）と、規則を**GitHub のマイルストーンに
  写す**書き方（実務の課題管理の構成は書けないので、公開仕様のある側に写しました）。
- ガード（`scripts/guard.ts`）と、**規則を 1 つずつ壊した陰性テスト**。規則が選んでいない番号、
  長さの上限、入力に出てこない番号、URL、`@` メンション、鍵とトークンの形、`password` と
  「パスワード」。
- 入力の正規 JSON のハッシュによる再利用。`narrative.sha` は**ガードが受理したときだけ**書きます。
  受理されなかった文のハッシュを残すと、翌日それが別の入力に再利用されます。
- A/B のサンドボックスと秘密情報の伏せ字（`harness/ab/`）。

## 動かし方

### まずオフラインで（`claude` を呼びません）

```bash
pnpm i
pnpm test          # 21 ファイル 226 本
pnpm lint          # Biome
pnpm typecheck     # tsc --noEmit
pnpm skills:validate
```

Node 24 と pnpm が必要です（pnpm の版は `package.json` の `packageManager` が決めます。
`corepack enable` はどこでも使いません）。Node は `.ts` をそのまま実行します。

### デモ（モックサーバを同一プロセスで立てます。外に出ません）

```bash
pnpm fetch:demo  -- --issue 101 --out out/fetch
pnpm digest:demo -- --mode collect-only --out out/digest
```

`out/` は git の無視対象です。`collect-only` は LLM を呼ばず、規則だけでページを書きます。

### スキルを別のリポジトリに入れる

```bash
cp -r skills/verifiable-fetch /path/to/your-repo/.claude/skills/
```

ディレクトリ 1 つで完結しています。`pnpm skills:validate` は任意のディレクトリにも使えます。

### `claude` を呼ぶコマンド（**使用量がかかります**）

```bash
# 起動率のプローブ（既定で 1 問 3 回。問い 20 問なら 60 回の呼び出し）
pnpm probe -- --skill skills/verifiable-fetch --queries evals/verifiable-fetch/trigger.json --runs 3

# A/B（スキルあり・なしの 2 本を同じモデルで）
pnpm ab -- --eval evals/verifiable-fetch/evals/screenshots-ja.json --runs 1

# ダイジェストのナレーション
pnpm digest:demo -- --mode preview --out out/digest
```

実行ごとの `total_cost_usd` は結果ファイルに残ります。**閾値の近くで低い率が出たときに、
良い数字が出るまで回し直さないでください。** それは測定ではありません。

ではありません**。実務の数字は 「背景」 の事例を参照してください（ここには書きません）。

### テストと検証

| `pnpm test` | 21 ファイル **226 本すべて成功** |
| `pnpm lint` | **61 ファイル**を検査、修正なし |
| `pnpm typecheck` | エラーなし |
| `pnpm skills:validate` | **3 skills: 3 ok, 0 failed, 0 warnings**（説明文 943 / 975 / 912 文字） |

### 起動率（1 問 3 回、陽性 10 問・陰性 10 問）

| スキル | 陽性 | 陰性 | 壊れた実行 | 閾値付近 | 費用 (USD) |
| --- | --- | --- | --- | --- | --- |
| `verifiable-fetch` | **10/10** | **10/10** | 0 | 0 問 | 5.3711 |
| `standup-digest` | **9/10** | **10/10** | **1（timeout）** | 1 問 | 5.4781 |
| `skill-trigger-probe` | **8/10** | **10/10** | 0 | 5 問 | 5.1671 |

起動率を良く見せるいちばん簡単な方法で、このスキルが存在する理由がそれです。

閾値の近くと出た問い（と落ちた問い）を **6 回で測り直しました**。7 問のうち 5 問が動き、
**2 問は合否そのものが入れ替わりました**。

| 問い | 3 回 | 6 回 |

| `pos-zh-which-skill-fired` | 0.67 (2/3) ✅ | **0.33 (2/6) ❌** |
| `pos-zh-token-cost` | 0.33 (1/3) ❌ | **0.50 (3/6) ✅** |
| `pos-en-twenty-queries` | 0.67 (2/3) | 0.83 (5/6) |
| `pos-en-before-shipping` | 0.67 (2/3) | 0.50 (3/6) |
| `pos-en-validate-frontmatter` | 0.00 (0/3) | 0.17 (1/6) |
| `pos-en-zero-on-windows` | 0.33 (1/3) | 0.33 (2/6) |
| `pos-ja-description-limit` | 0.67 (2/3) | 0.67 (4/6) |

3 回で得られる率は 0、0.33、0.67、1 の 4 通りだけで、**閾値の 0.5 はそもそも出ない値**です。
上の表の 8/10 と 9/10 も 3 回のもので、6 回で測り直すと **8/10 は 7/10 になり、9/10 は 10/10 に

この実行は**それを自分自身の上で測りました**。

### A/B（スキルあり・なし。10 本の腕、計 14 回の実行。全 14 回が完走）

`with` の腕 7 回すべてで `skillInInit` が `true`、`without` の腕 7 回すべてで `false` でした。

| eval | 機械判定 with ÷ without | 判断 with ÷ without | 2 回が一致 |
| --- | --- | --- | --- |
| `screenshots-ja` | 4/4 ÷ **4/4** | 2/2 ÷ 1/2 | （1 回のみ） |
| `blocked-and-large-en` | 5/5 ÷ **5/5** | 1/1 ÷ 0/1 | （1 回のみ） |
| `deep-path-zh` | 4/4 ÷ 1/4 | 1/1 ÷ 0/1 | （1 回のみ） |
| `preview-zh` | 12/12 ÷ 1/12 | 4/4 ÷ 0/4 | with: yes ／ without: **yes（空。どちらもページを作らなかった）** |
| `decisions-only-ja` | 8/8 ÷ 4/8 | 2/2 ÷ 0/2 | with: yes ／ without: **no** |

**何が差を生んでいるか。** `deep-path-zh` と `preview-zh` の差は大きく、素のエージェントは
深いパスの規則と、ページの書式の規則を再現できませんでした。`decisions-only-ja` では
`without` の 2 回が**同じデータから違う答え**を出しました（`no`）。毎日同じ一覧が出ることに
価値があるというのが、このスキルの出発点です。

**差がゼロの 2 本を、ゼロとして載せています。** `screenshots-ja` と `blocked-and-large-en` の
機械判定は完全に同点です。素のエージェントでも添付の検証はできました。差が出たのは判断の側
（失敗の報告が読んで分かるか）です。**差を作るために eval を書き換えてはいません。**

**`preview-zh/without` の「一致」は一致ではありません。** 2 回とも**ページを 1 枚も作らなかった**
ための一致です。空の一致が同意に見えないよう、ベンチマークは `agreementTrivial` を記録し、
表には `yes (empty: neither run produced one)` と書きます。

## 制約・既知の限界

数字の読み方として、以下は**控えめな注意書きではなく、具体的な限界**です。

### 測定そのものの限界

- **A/B の回数が少なすぎます。** 1 本の腕あたり 1 回か 2 回です。上の 3 回 → 6 回の表が示すとおり、
  この回数では差の大きさを言えません。言えるのは、この 14 回でこうなったということだけです。
- **判断の採点は人が付けたものではありません。** この実行のエージェント自身が、記録から引用した
  証拠つきで付けました。証拠は `grading.json` に残してあるので、読み手は採点に同意しないことが
  できます。採点者が自動で「おそらく通った」と書く経路はありません（未採点は `passed: null`）。
- **いくつかのアサーションは、スキル自身の規則をそのまま符号化しています。**
  フィクスチャとスキルが同じ知識から作られていると、試験問題を教えているのと変わりません。
  期待される結果の表が実装より先に外から与えられていることで弱めてはいますが、消えていません。
  この点は [docs/reading-evals.md](docs/reading-evals.md) の 5 節に詳しく書きました。
- **汚染スキャナの 14 件のフラグは、14 件の逸脱ではありません。** 読み直した内訳は
  スキャナの誤検出 3 件（API の経路を散文として書いた行をパスと読んだもの）、共有の `/tmp` への
  書き込み 5 件、`/dev/null` 6 件です。誤検出はスキャナ側の既知の欠陥として記録してあり、
  **測定後にスキャナを直していません**（直せば測り直しになります）。
- **`preview-zh/without` の「一致」は、どちらもページを作らなかったための一致です。**
  一方、同じ `decisions-only-ja` の `without` は、同じデータから 2 回で違う答えを出しました。
- **A/B の中の入れ子のナレーション呼び出しには、設計どおり資格情報がありません**（F9、F10）。
  そのためダイジェストは劣化版のページを書きました。**これは期待どおりの動作で、失敗ではありません。**
  腕に資格情報を渡して見栄えを良くすることはしていません。
- **思考トークンの 4 つの数字からは、何の結論も出ません。** この README もそう読める書き方を
  していません。

### 記録と秘密情報

- **`run.json` は、契約により、モックが発行したトークンの「値」を記録します。** コミットされた
  結果に入っているのは、もう存在しないサーバーが 300 秒だけ有効にした 32 桁の 16 進数のダミーです。
  ただし、**この取得器を本物のトラッカーに向ければ、本物の署名付き URL の資格情報が、
  コミットされる結果ファイルに残ります。** 公開前の手当ては
  [PUBLISHING.md](PUBLISHING.md) の 3 節に書きました。
- **ページの末尾のハッシュは `facts.json` のハッシュです。** API のページサイズが変わると
  リクエスト数が変わるので（26 件と 49 件、F25）、読み手が気にする事実がすべて同一でも
  ハッシュは動きます。**内容の指紋ではありません。**

### 対象の限界

- **モックは本物のサービスではありません。** 形は本物の応答に照らして確かめましたが、
  確かめた日付は F16〜F19 のとおりです（2026-10-02）。本物の側が変われば、合っているのは
  モックまでです。
- **測定した CLI の挙動は 2.1.233 のものです。** 起動分類も、フラグの受け付け方も、
  別の版では別の結果になりえます。
- **GitHub の未認証のレートリミットがあります**（F16、1 時間 60 回）。モックに向けている限り
  当たりませんが、本物に向けるときは効きます。
- **`pnpm fetch:demo` は実行ごとに空きポートを取ります。** そのため、生成されるページの URL の行は
  2 回の実行で 1 か所だけ違います（F24）。同一性を確かめるときは、そこを除いて比べます。
- **Windows ではここでは動かしていません。** テスト、`pnpm skills:validate`、プローブを
  Windows で回すのは、このリポジトリを受け取った後の手順です。F13 と F22 は、同じ骨組みが
  Windows で動いたという**過去の観測**であって、この版をそこで回した証拠ではありません。
  CI の `windows` ジョブはそのために置いてあります。

## 作り方

**このリポジトリは、無人の goal-bus 実行によって作られました。** 人が各ゴールのレビューをする
代わりに、Stop フックが完了したゴールを審査して PASS か REJECT を返し、PASS のときは次のゴールの
指示を渡します。作業者（Claude Code）はゴールを 1 つずつ受け取り、G0 から G5 までの 6 ゴールで
このリポジトリを作りました。

- [goal-pack/](goal-pack/) — 実行に使った資料がそのまま入っています。
  - [`SCOPE.md`](goal-pack/SCOPE.md) — 凍結された契約。各ファイルが何であるべきかと、期待される
    結果の表。実装が表と食い違ったときに直すのは実装の側です。末尾に **AS-BUILT** として、
    契約との差分を 1 つずつ理由つきで記録しました。
  - [`facts.md`](goal-pack/facts.md) — 外部の挙動について**観測した日付つき**の事実
    （F1〜F28）。測定中に見つけた 6 件（F23〜F28）は実行中に追記したものです。
  - [`PROGRESS.md`](goal-pack/PROGRESS.md) — 全 54 行の受け入れ条件と各ゴールの判定、引用した
    証拠、付随所見、ゴールごとのコミットメッセージ案。
  - [`materials/practice.md`](goal-pack/materials/practice.md) — 元になった実務の記録。

評価が実装を直した例、測定の途中で見つけて直した欠陥、そして測り直すために破棄した費用も、
すべて `PROGRESS.md` に残っています。
