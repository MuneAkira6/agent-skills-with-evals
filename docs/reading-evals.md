# 評価の読み方

このリポジトリの評価スイートは、実務で 3 本のスキルを使ってきた中で残った 6 つの教訓から作られて
います。以下はその教訓と、**このリポジトリのどこがそれを示しているか、あるいはどこで防いでいるか**
の対応です。数字はすべて `evals/*/results/` にある 2026-10-05 の実行から引いています。

教訓そのものは `goal-pack/materials/practice.md` の第 5 節が出どころです。

---

## 1. 基準線は、すでに公開された成果物を読んで汚染されることがある

スキルを与えた腕（`with`）と与えない腕（`without`）を比べるとき、`without` の腕がどこかで
スキルの成果物を読んでしまうと、比較そのものが無意味になります。公開済みの README や過去の
出力がリポジトリの中にあると、エージェントはそれを読んで「正解」を再現できてしまいます。

**このリポジトリでの防ぎ方**

- A/B の腕はすべて、OS の一時ディレクトリに作った**空の作業ディレクトリ**で動きます。
  リポジトリの中では一度も動きません（`harness/ab.ts`、各 `run.json` の `wsPath`）。
- `without` の腕には `.claude/skills/` を置きません。観測として `skillInInit` を記録し、
  14 回の実行すべてで `with` が `true`、`without` が `false` であることを確かめています。
- 汚染スキャナ（`harness/ab/contamination.ts`）が 3 つの規則で記録を走査します。腕の一時
  ディレクトリの外のパス、ローカルでない URL のホスト、そして **`without` の腕がスキル
  ディレクトリに言及したこと**。3 つ目がこの教訓そのものに対応する規則です。
- フラグが出たら、消さずに `run.json` に残して読みます。この実行では 14 件出ました。内訳は
  スキャナの誤検出 3 件（API の経路を散文として書いた行をパスと読んだもの）、共有の `/tmp` への
  書き込み 5 件、`/dev/null` 6 件です。**14 件の逸脱ではありません。**

**読むときの注意**：フラグが 0 件であることは、汚染がなかったことの証明ではありません。
スキャナが見る 3 つの規則に当てはまらなかった、というだけです。

## 2. その日の事実に釘付けした断言は、数日で腐る

「GitHub の未認証レートリミットは 1 時間 60 回」「タイムラインの `committed` は
`committer.date` を持つ」——こうした断言は、観測した日には正しく、半年後には正しいとは限りません。
評価の中に日付のない断言を書くと、ある朝、誰も触っていないのにテストが落ちます。

**このリポジトリでの防ぎ方**

- 外部の形に依存する事実は、すべて `goal-pack/facts.md` に**観測した日付つき**で書いてあります
  （F16 のレートリミット、F17 の `submitted_at`、F18 のタイムライン、F21 の Actions の SHA）。
  腐ったときに、どの断言がいつの観測に基づくのかを探さずに済みます。
- テストは生きている API を呼びません。`harness/mocks/` のモックが、記録した**形**を返します。
  形が変わったら直すのはモック 1 か所で、226 本のテストの側ではありません。
- 時刻は引数です。ダイジェストは `--now 2026-10-05T09:00:00Z` を受け取り、時計を読みません。
  「3 日前」のような判定が、実行した日によって変わらないようにするためです。
- それでも腐るところは、腐ると書いてあります。F24（デモが空きポートを取るので、ページの URL 行は
  実行ごとに動く）、F25（`facts.requests` は API のページサイズで 26 件と 49 件に変わるので、
  同一性の検査では正規化する）、F23（`pnpm i` が新しいパッチを引くことがある）。

**読むときの注意**：`evals/*/results/` の数字は 2026-10-05 の、Claude Code 2.1.233 の、
`claude-sonnet-5` のものです。別の日・別の版で測り直した数字は、別の数字です。

## 3. 差がゼロでも、それが正しい結果のことがある

スキルを入れても出力が変わらないことがあります。スキルの修正が、出力ではなく読み手の理解を
正すものだった場合がそうです。このとき、差を作るために問題をこしらえてはいけません。

**このリポジトリでの示し方**

10 本の腕のうち 2 本は、機械判定が**完全に同点**でした。

| eval | with | without |
| --- | --- | --- |
| screenshots-ja | 4/4 | 4/4 |
| blocked-and-large-en | 5/5 | 5/5 |

これは「スキルに効果がなかった」とも読めますが、そう書くのは早すぎます。同じ腕の**判断**の
評価は 2/2 ÷ 1/2、1/1 ÷ 0/1 で割れています。機械判定が見ているのは「添付が検証されたか」で、
判断が見ているのは「失敗の報告が読んで分かるか」です。前者は素のエージェントでもできました。

同点を同点として出すために、この 2 本の eval は**書き換えていません**。アサーションを足して
差を作れば、作った差を測ることになります。

**裏側の教訓**：逆に、一致を「一致」と読んではいけない場合もあります。`preview-zh` の
`without` 腕は 2 回の実行が「一致」しましたが、**どちらもページを 1 枚も作らなかった**ための
一致です。空の一致を同意と読まないために、ベンチマークは `agreementTrivial` を記録し、表には
`yes (empty: neither run produced one)` と書きます。同じ `decisions-only-ja` の `without` 腕は、
同じデータから 2 回で**違う答え**を出しました（`no`）。

## 4. サブエージェントの報告は証拠であって、結論ではない

「原因はここです」という報告は、確かめるとすぐに崩れることがあります。報告は、読んで確かめる
ための材料です。

**このリポジトリでの防ぎ方**

- 判断の評価は、採点者が自動では埋めません。`grade()` は `passed: null` と空の証拠を返し、
  人が `grading.json` に書き込むまで未採点のままです（`evals/*/grade.ts`）。
  **採点者が「おそらく通った」と書く経路がありません。**
- ナレーションは、LLM が書いた文をそのまま載せません。ガードが検査し、規則が選んでいない番号、
  長さの上限を超えた文、ナレーション入力に出てこない番号、URL（`http://`・`https://`・`www.`）、
  `@` メンション、鍵とトークンの形（3 種）、`password` と「パスワード」を拒否します。
  2 回拒否されたら、ページは機械判定だけの劣化版を書いて正常終了します
  （`skills/standup-digest/scripts/guard.ts`、`test/digest-guard.test.ts`）。
- 報告が崩れた実例が、この実行の中にあります。汚染スキャナが出した 14 件のフラグを**読み直したら
  3 件は誤検出**でした（`goal-pack/PROGRESS.md` の付随所見 4）。スキャナの出力を結論として
  「14 件の汚染」と書いていたら、間違った報告になっていました。

**読むときの注意**：このリポジトリに記録されている判断の採点は、この実行のエージェント自身が、
記録から引用した証拠つきで付けたものです。**人が付けた採点ではありません。** 証拠の引用は
`grading.json` に残してあるので、読み手は採点に同意しないことができます。

## 5. フィクスチャとスキルが同じ知識から作られていると、試験問題を教えているのと変わらない

スキルの規則を書いた人が、その規則を確かめるフィクスチャも書くと、評価は「規則が規則どおりに
動くこと」しか測れません。スキルが**間違った規則**を持っていても、フィクスチャが同じ間違いを
持つので、通ってしまいます。

**このリポジトリでの防ぎ方と、残っている弱さ**

- 期待される結果の表は、スキルの実装より**先に、外から**与えられました
  （`goal-pack/SCOPE.md` の expected-outcome table）。実装が表と食い違ったとき、**直すのは
  実装の側**です。この実行では実際に 3 回、与えられた表が実装を直しました。
  - `#191` に `carryover` のトリガーが付いていた。契約は「silent でない項目にのみトリガーが
    立つ」と書いてあり、`triggersOf` が silent の項目に `[]` を返すように直した。
  - `preview-zh` の M3：待ちの PR が項目自身のときに番号を二度名乗っていた。
  - `preview-zh` の M2：`PR #221` は issue 番号ではない（F27）。
- フィクスチャは実務のチケットではなく、`harness/mocks/` の作り物です。本物のトラッカーの
  代わりではありません。形は F16〜F19 の日付に確かめたものです。

**残っている弱さ（隠さずに書きます）**：いくつかのアサーションは、**スキル自身の規則を
そのまま符号化しています**。たとえばダイジェストの採点は、スキルが定めた lane と trigger の
名前で判定します。これは第 5 節の教訓がまさに警告している形です。外から与えられた期待表が
あることで弱められてはいますが、消えてはいません。

## 6. 回数が少ないと、起動率の 3 分の 1 と半分を見分けられない

同じ問いを 3 回しか回さないと、得られる率は 0、0.33、0.67、1 の 4 通りしかありません。
**閾値の 0.5 は、そもそも出ない値です。** 0.67 と 0.33 の差が、スキルの差なのか、
3 回の揺れなのかは分かりません。

**このリポジトリでの示し方——この実行は、これを自分自身の上で測りました**

3 回で測ったあと、閾値の近く（`nearThreshold`）と出た問いと、落ちた問いを 6 回で測り直しました。
7 本のうち **5 本が動き、そのうち 2 本は合否そのものが入れ替わりました**。

| 問い | 3 回 | 6 回 | 動いたか |
| --- | --- | --- | --- |
| `pos-zh-which-skill-fired` | 0.67 (2/3) ✅ | 0.33 (2/6) ❌ | **合否が入れ替わった** |
| `pos-zh-token-cost` | 0.33 (1/3) ❌ | 0.50 (3/6) ✅ | **合否が入れ替わった** |
| `pos-en-twenty-queries` | 0.67 (2/3) | 0.83 (5/6) | 動いた |
| `pos-en-before-shipping` | 0.67 (2/3) | 0.50 (3/6) | 動いた |
| `pos-en-validate-frontmatter` | 0.00 (0/3) | 0.17 (1/6) | 動いた |
| `pos-en-zero-on-windows` | 0.33 (1/3) | 0.33 (2/6) | 動かなかった |
| `pos-ja-description-limit` | 0.67 (2/3) | 0.67 (4/6) | 動かなかった |

**だから、閾値の近くの 3 回の率は率ではありません。** それは 3 回の結果です。
このリポジトリが出している 8/10 と 9/10 という見出しの数字も 3 回のもので、6 回で測り直すと
8/10 は 7/10 になり、9/10 は 10/10 になります。両方を載せているのは、どちらかが正しいから
ではなく、**3 回では決まらないことがこの数字で見えるから**です。

6 回でも足りません。6 回で得られる率も 7 通りで、0.50 と 0.33 の違いは 1 回の実行です。
プローブが `nearThreshold` を記録するのは、その問いの率を信じるなという印をつけるためです。

**読むときの注意**：プローブは**壊れた実行を陰性として数えません**。起動分類は壊れた理由
（`spawn-error`、`timeout`、`no-init`、`no-result`、`auth`、`not-loaded`）を先に見て、
壊れていたらその回を有効回数から外します。この実行では `neg-zh-review-pr` が 1 回
タイムアウトし、**壊れた実行として報告しました**。陰性 10/10 の分母には入っていません
（`"brokenRuns":{"timeout":1}`、`"incomplete":true`）。壊れた実行を陰性として数えるのが、
起動率を良く見せるいちばん簡単な方法であり、このスキルが存在する理由です。
