# 素材：著者のスキルと評価の実践（このリポジトリを書くための一次資料）

> ワーカーへ：著者の実務について書いてよいことは、このファイルがすべてです。ここにないことを実務の話として書かないでください。書き方は自分の言葉で。実務の数字（件数、割合、トークン数、日付、時刻）は一つも書きません。README の「結果」は事例へのリンクで示します。会社・製品・チーム・人の名前は出てきませんし、書いてもいけません。サンプルの製品は架空の「Acme Tasks」です。

## 1. 状況

- エージェントに任せる仕事が増え、同じ説明を何度もプロンプトに書く無駄が目立つようになりました。そこで、繰り返す手順を Claude Code のスキルにまとめていきました。
- スキルが増えると、担当範囲の重なりと、直したときに本当に良くなったのか分からないことが問題になりました。

## 2. スキルの書き方

- 説明文には「何をするか」「いつ使うか」に加えて、「何には使わないか」を書きます。似たスキルがあるときは、その名前と、区別の軸（どの環境か、ブラウザを使うか、どのサービスか など）を書き入れます。説明文に「しないこと」がないと、似たスキルの間で取り合いが起きます。
- 本文は手順の要点だけにして、細部は参照ファイルに分けます。決まった処理はスクリプトにして、エージェントには呼び出させます。

## 3. 評価の取り方

- スキルあり・なし、または改修前のスナップショットとの A/B で比べます。両方の腕で同じモデルを使います。
- 採点は、機械で決められるチェックと、証拠を引用して答える判断問題を組み合わせます。
- 回ごとに、結果の読み方を書き残します（基準線が汚染されていないか、その問題が差を生む力を持っているか）。
- 評価で見つかった欠陥は、スキル本体に戻します。評価の目的は点数より、欠陥を見つけることです。

## 4. 起動判定

- 公式の評価ツールの起動判定は、Windows では毎回「起動しなかった」と報告し、しかもそれが失敗に見えませんでした。そこで、CLI を実際に起動して出力の中にスキルの呼び出しがあるかを数える、自前のプローブで置き換えました。
- 出力が空だった実行は、「起動しなかった」ではなく「測れなかった」として別に数えました。測定器が黙って壊れていても、「スキルが起動しない」という結果に見えてしまうからです。
- このプローブが数えるのは「そのスキルが起動したか」だけで、「どのスキルが起動したか」ではありませんでした。ゼロには「何も起動しなかった」と「別のスキルが勝った」の両方があり、直し方は正反対です。
- 説明文が公開仕様の上限を超えていて、末尾の除外条項がモデルに届かない状態になっていたのを、検証ツールで見つけました。

## 5. 評価の読み方として残した教訓

- 基準線は、すでに公開された成果物を読んで汚染されることがある。
- その日の事実に釘付けした断言は、数日で腐る。
- 差がゼロでも、それが正しい結果のことがある（スキルの修正が、出力ではなく読み手の理解を正すものだった場合など）。差を作るために問題をこしらえない。
- サブエージェントの報告は証拠であって結論ではない。報告された原因が、確かめるとすぐに崩れることがある。
- フィクスチャとスキルが同じ知識から作られていると、試験問題を教えているのと変わらない。
- 各問を少ない回数しか回さないと、起動率の 3 分の 1 と半分を見分けられない。閾値の近くは回数を増やして測り直す。

## 6. 取得したチケットや wiki ページを手元に残すスキル

- チケットやページを Markdown と添付ファイルとして保存するスキルを使っていました。
- 添付の取得が成功したかは、「保存したバイト数がメタデータのサイズと一致したか」だけで判断しました。中継装置が返す 403 のエラーページも、それらしいファイルとして保存されてしまうからです。
- ログに出す URL では、署名付き URL の署名部分を伏せました。
- Windows ではパスが長すぎると、ディレクトリをたどる道具がエラーを出さずに空の結果を返すことがありました。保存先のパスは短く保ちます。
- 画像は、リンクを置くだけでなく、何が写っているかを文章で書き残しました。後で検索する人には、そのほうが役に立ちます。

## 7. 朝会ダイジェスト

- 平日の朝会の前に、課題管理と GitHub の状況から朝会用のページを自動で作っていました。
- 規則で決められる部分（泳道、今日決めること、並び順）は規則で決め、LLM は規則が選んだ項目について短い文だけを書きます。LLM の文はガードを通し、存在しない番号への言及、長すぎる文、URL や秘密情報を含むものは捨てます。ガードを通らなければ、機械の文だけでページを出します。表こそが本体だからです。
- 毎回違う一覧を出す既存の AI 機能は採用しませんでした。同じデータからは毎日同じ一覧が出ることに価値があります。
- 「今日決めること」の件数は固定しません。規則に当たった項目がすべて載り、ない日は「ない」と書きます。
- 「動き」として数えるのは、状態の遷移、コメント、PR の更新、本文の編集だけです。スプリント計画で一斉に行う移動や担当替えは数えません。それらは更新日時をまとめて新しくしてしまい、長く誰も触っていない項目を隠すからです。長く動きのない項目は、決めごとに載せず、番号を並べるだけにしました。
- 朝会に出ない人が担当の項目は、決めごとに載せません。その場に決める人がいないからです。
- 進捗のない項目は「発言不要」として名前を出し、黙ることに正当性を与えました。
- ページのコメント欄が、翌日の AI への指示の窓口です。変えられるのは書き方だけで、事実は変えられません。
- 費用は自分で負担していたので、安く済む作りにしました。CLAUDE.md のないディレクトリで CLI を動かし、システムプロンプトを差し替え、ツールと MCP を外し、入力を絞り、思考はその 1 回の呼び出しのプロセスにだけ環境変数で止めました（設定ファイルには書かず、ほかのセッションに影響させない）。入力が前回と同じなら、ガードを通った前回の文を使って呼び出しません。呼び出しごとの使用量は記録しました。
- 評価で、並び順の点数が同じ停滞を二重に数えていた欠陥が見つかりました。足し算をやめて大きいほうだけを取り、何度も機会があった慢性の項目は割り引くようにしました。

## 8. 書いてはいけないこと

- 実務の数字（件数、割合、トークン数、費用、日付、時刻、人数）。
- 課題管理や wiki、チャットの具体的なサービス構成、スペースやボードの名前、URL、アカウント。
- 朝会の出席者や、特定の誰かについての記述。
- 評価で見つかった欠陥のうち、製品やサービスの弱点にあたるもの。上の 7 の並び順の欠陥は、このスキル自身の欠陥なので書いて構いません。

## 9. 実務とデモの書き分け

README では「実務で実施した点」と「デモで追加した点」を分けて書きます。上の 2〜7 にあるものが前者です。このリポジトリで新しく作るもの（公開仕様と出典を付けたフロントマターの検証、測れなかった実行を理由ごとに分ける判定、どのスキルが起動したかの記録、閾値付近の警告、設定を分離した測定、Redmine 形のモック、GitHub REST 形のモック、A/B のサンドボックスと秘密情報の伏せ字、GitHub のマイルストーンへの規則の写し方、など）は後者です。
