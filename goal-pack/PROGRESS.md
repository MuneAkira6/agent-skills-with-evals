## Handover (filled at the end; each item = fact, impact, the decision needed)

Eight items. Each is a fact this run established, what it costs if ignored, and the decision that is
not mine to make.

1. **Windows was never run on this version.** *Fact:* the contract puts it out of scope; F13 and F22
   are observations from 2026-10-02 on the author's Windows PC, not from this build. *Impact:* the
   `windows` job of CI has never executed, so "portable by construction" is an argument, not a
   measurement — and the probe's original reason for existing is a Windows-only failure of someone
   else's trigger detection. *Decision needed:* run `pnpm test`, `pnpm skills:validate` and one probe
   on Windows before trusting any cross-platform claim, or let the first CI run on a pull request do
   it and read the result.

2. **A trigger rate near the threshold is not a rate.** *Fact:* at six runs instead of three, five of
   the seven re-measured queries moved and two verdicts flipped (`pos-zh-which-skill-fired` 0.67→0.33,
   `pos-zh-token-cost` 0.33→0.50). *Impact:* the committed headline figures 8/10 and 9/10 would read
   7/10 and 10/10 at six runs; anyone quoting one of them as *the* rate is over-reading it. *Decision
   needed:* how many runs the author is willing to pay for before publishing a rate — and whether the
   README should lead with the six-run numbers instead of both.

3. **`pos-en-validate-frontmatter` triggers 1 time in 6.** *Fact:* 0.00 at three runs, 0.17 at six;
   the query is a plain English request to validate a skill's frontmatter, which is the skill's most
   direct purpose. *Impact:* the description may be losing to a sibling or may simply not match the
   wording; `siblingsFired` recorded `update-config` firing 3 times in that probe, so both readings
   are live. *Decision needed:* AC-38 froze the three descriptions for the whole run, so this cannot
   be fixed inside it. Editing the description afterwards invalidates every rate measured here — so
   the decision is whether to re-measure all three skills after an edit, or publish as measured and
   treat the edit as a separate round.

4. **The judgment grades are the run's own agent's.** *Fact:* every judgment assertion was graded by
   me, with evidence quoted into `grading.json`; `grade()` cannot fill them (`passed: null`, empty
   evidence). *Impact:* a reader who disagrees with a grade can check the quotation, but there is no
   independent grader anywhere in the numbers. *Decision needed:* whether to re-grade the 14 runs'
   judgment assertions by hand before publishing, or publish with the limitation stated — the README
   and `docs/reading-evals.md` currently state it.

5. **`run.json` persists issued signed-URL token values.** *Fact:* the contract requires the issued
   tokens to be recorded, and two eval assertions read them; committed results therefore hold 32-hex
   dummies from an ephemeral mock. *Impact:* pointing this runner at a service that issues real
   signed URLs would write real credentials into files intended to be committed. *Decision needed:*
   change `harness/ab/mocks.ts` to record a count instead of values **before** any run against a real
   tracker, and accept that the two assertions must then be rewritten. PUBLISHING.md part 3 carries
   this as a checklist item.

6. **The contamination scanner has a known false positive.** *Fact:* its absolute-path pattern reads
   an API route written as prose as a filesystem path — 3 of this run's 14 flags. *Impact:* flag
   counts in these results are inflated, and a future reader who trusts the count without re-reading
   the flags will over-report escapes. *Decision needed:* which of the two candidate fixes in
   incidental finding 4 to take. It was deliberately **not** fixed here, because changing the scanner
   after the measurement would mean re-measuring.

7. **Several assertions encode the skills' own rules.** *Fact:* the digest's graders judge by the lane
   and trigger names the skill itself defines; materials section 5 warns that fixtures and skill from
   the same knowledge is teaching the exam. *Impact:* those assertions cannot catch a wrong *rule*,
   only a rule applied inconsistently. The mitigation is real but partial: the expected-outcome table
   came from outside and corrected the implementation three times. *Decision needed:* whether to
   commission a second set of expected outcomes written by someone who has not read the skills.

8. **`scoreOf`'s two switches stay in the shipped code.** *Fact:* `chronicDiscount` and
   `sumInsteadOfMax` exist only so tests can show the two formula choices matter; nothing in the
   pipeline passes them and `digest.config.json` has no key for either. *Impact:* a future reader may
